# Seguridad de la implementación base

Este documento describe los controles de la versión segura. La versión vulnerable omite deliberadamente algunos controles para mostrar seis fallas en un laboratorio local; no debe exponerse a redes no confiables. Este informe no es una certificación.

- La sesión está en el servidor mediante Flask-Session y CacheLib; cada instancia tiene directorio y cookie distintos. El identificador rota al iniciar sesión; cierre y vencimiento invalidan la sesión. El restablecimiento cambia una generación persistida y hace inválidas las sesiones anteriores.
- Las contraseñas usan las primitivas de Werkzeug. Para el laboratorio se inicializan tres cuentas ficticias con la contraseña pública `Demo1234!`; nunca utilizar esos datos fuera del laboratorio.
- Las operaciones administrativas verifican el rol en el servidor. Las búsquedas usan parámetros. Las mutaciones exigen token CSRF y verifican el origen si el navegador lo envía. No se almacenan importes de dinero en punto flotante.
- Las transferencias y los ajustes emplean una transacción SQLite; el débito condicional evita sobregiros concurrentes. Los datos iniciales pueden restablecerse sólo a través de un listener interno separado, autenticado por un secreto compartido y sin puerto publicado. La coordinación de dos bases no es una transacción distribuida.
- La consulta de cotización acepta exclusivamente la URL fija del proveedor simulado, sin redirecciones, con límite de tiempo y tamaño de respuesta; el proveedor y el fixture interno no publican puertos al host. La red Docker interna es una medida de contención, no una frontera absoluta de seguridad del host.
- La caché de sesiones debe permanecer privada: el serializador predeterminado de CacheLib FileSystemCache usa pickle. No montar en directorios modificables por usuarios no confiables ni guardar allí archivos subidos.
- El runtime está destinado a un único proceso por aplicación: el candado de mantenimiento y el reinicio coordinan sus hilos, no procesos independientes. Una pasarela de destinos fijos publica los puertos únicamente en `127.0.0.1`; las aplicaciones y los fixtures permanecen en la red interna sin puertos publicados.
- El servidor usa HTTP local y datos sintéticos; no se debe desplegar como una billetera real, ni exponer a redes no confiables. La compilación de imágenes descarga paquetes e instala Chromium; se debe construir y probar antes de una demostración sin conexión.
- La versión segura limita los intentos de acceso a cinco por cuenta y veinte por dirección IP durante 60 segundos; devuelve la misma respuesta ante credenciales incorrectas y usuario inexistente. El límite es local a cada instancia, no distribuido.
- El cliente HTTP del cotizador no sigue redirecciones ni toma proxies de variables de entorno, limita el tamaño, comprueba formato y utiliza tiempos de conexión y lectura. La confianza en el nombre del proveedor depende del DNS interno de Docker y de que sólo servicios autorizados se conecten a esa red; no es una solución general contra suplantación de DNS.
- Las verificaciones de origen complementan el token CSRF; se admiten clientes sin cabecera `Origin` si presentan el token válido. Una política CSP y `nosniff` complementan el renderizado de texto en la versión segura.

Verificación integrada: `python -m pytest tests -q --basetemp=.test-tmp-local` aprobó 21 pruebas de backend, guía y pasarela. El uso de `--basetemp` en Windows mantiene los temporales dentro del proyecto. La ejecución de contenedores y navegador completó las doce observaciones esperadas; se documenta en `INFORME.md` con las capturas exportadas. Al trasladar el laboratorio al equipo de exposición conviene repetir el lote desde la guía. Tras actualizar Flask, pytest y requests, la auditoría del archivo de versiones Python no encontró vulnerabilidades conocidas; alcance y límites en `INFORME.md`. `docker compose config --quiet` verifica la configuración y no reemplaza las comprobaciones realizadas sobre los servicios en ejecución.
